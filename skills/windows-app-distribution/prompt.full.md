# Procedure

Deliver the Windows distribution work the user requested. Start with the existing product,
not with SchemaCraft's implementation or a preferred installer.

## Identify scope and change

Determine whether the user needs advice, design, local implementation, artifact verification,
listing preparation, publication or a delivery check. Read project instructions, architecture,
channel workflows and previous release evidence as applicable. Do not turn analysis into
implementation or stop at a plan when authorized implementation was requested.

Classify the change as first release, product/payload, packaging/identity/signing/runtime,
listing-only, or internal documentation. A listing-only revision retains the package version
when the artifact is unchanged; new compatibility claims still need supporting evidence.
Record the listing/submission revision separately. Select the matching guide sections.

Reuse known decisions and existing authorization. Ask only unresolved questions that materially
change the result, one product decision at a time. Continue independent preparation while
waiting. Do not require a fixed intake form, particular technology, VM, new branch/PR or every
release test merely because the skill was selected.

## Establish the applicable channel contract

Identify supported platforms, package format, runtimes, privileges, stable identities, data
ownership, update owner and direct-download requirements. If monetized, identify the channel's
entitlement authority and offline/outage policy without assuming transferable purchases.
Treat publisher-account eligibility and current Store rules as product-specific checks.

Separate packaging, signing and publication from common product behavior. Encapsulate required
channel integrations instead of duplicating business rules. When independent distribution is
required, retain a usable direct channel without Store credentials. Select concrete guards
from the actual stack/repository; distinguish proposed checks from implemented enforcement.

For signing/provenance work, identify each transformation and the expected hash/signature at
that stage. A signed EXE can differ from its unsigned input; do not require universal hash
equality or treat a checksum as proof of publisher trust. Verify applicable signing requirements
with current primary sources. Do not import certificates or change trust as a test shortcut.

## Prepare or execute the requested work

Reuse the project's release pipeline and configuration. Make only changes needed for the
requested outcome. Do not rebuild an unchanged binary for a listing edit, replace published
artifacts under an existing version, or force one verified-executable recipe on another stack.

Select channel-required checks and changed-risk scenarios, including the actual installed
context where relevant. Explain evidence reuse by artifact identity, environment and coverage.
Keep project deferrals explicit; they cannot waive channel requirements. Plan recovery with
version ordering and data compatibility rather than assuming an old package downgrades users.

Before a real-app session, use synthetic files/accounts and protect existing user state. Locate
effective packaged/unpackaged data paths, back up/isolate as agreed, restore after confirmed
process exit and verify integrity. An isolated About launch does not establish preservation
of projects or credentials across an update.

Prepare listings/reviewer material locally. Verify persistence after reopening the portal when
authorized. On failure, preserve the draft/error and limit attempts to those justified by new
evidence. If required information or essential reviewer access remains unavailable, mark
submission preparation blocked with the prerequisite, next action and owner. Continue dependent
submission only after that requirement or an authorized functional alternative is verified.
An optional field label is not permission to skip a review path the product needs.

Submission, publication, account, payment, signing-service and certificate operations require
applicable user authorization and the client's action policy. The skill grants none. Prepare
the concrete result before any necessary confirmation. Do not schedule unrequested monitoring.

## Verify the actual outcome

Separate package validation, certification, publication, public visibility and delivered version.
For changed deliverables, verify the actual customer route and installed identity/version/
signing origin; apply relevant real-app scenarios. For listing-only changes, check saved/public
content and reuse applicable artifact evidence instead of automatically installing/launching.
Observe the intended locale/market; a publisher session or old public link alone does not prove
new-version public delivery.

Deliver the output contract. Distinguish changed, proposed, executed, reused, failed, deferred
and unavailable work. Preserve historical evidence and label superseding records. If a tool or
policy constraint prevents a check, explain its narrow impact without inventing a pass or
expanding into unrelated infrastructure work.
