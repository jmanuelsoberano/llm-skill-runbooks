# Output contract

Use the user's language for the response and project conventions for code/artifacts. Scale the
result to the request; these are semantic requirements, not mandatory headings or a large table.

Include:

1. **Outcome and scope:** requested result, phase/change class and affected channels.
2. **Decisions or changes:** concrete result and reasons; distinguish implementation, proposals
   and unresolved choices. Link actual changed files/artifacts when available.
3. **Verification and evidence:** what was checked and what each observation proves. Where
   relevant, identify artifact/version, source revision, transformation/signing stage,
   environment, time and evidence reference. Explain reuse and its limits.
4. **Remaining work:** failures, blockers, deferred/unavailable checks, required decisions and
   next action/owner when known. Identify external actions still requiring authorization.

For implementation, deliver local changes and appropriate verification, not only a plan.
For advice, deliver the recommendation without modifying the app. A listing revision need not
introduce a package version or fresh installation test.

For substantive release records, distinguish check states: proposed, implemented/not run,
passed, failed, reused with rationale, not applicable with rationale, deferred with decision,
or blocked. Apply states only where useful. Publication/delivery need their own observations;
generated files, static validation and written evaluation cases do not establish them.

Do not claim current policy, signature trust, account eligibility, runtime compatibility,
cross-channel state sharing, update preservation or public availability beyond inspected
evidence. Cite primary sources near researched volatile claims and state access limitations.
Keep private evidence and secrets out of shared documentation.
