# HU, requisitos y documentación

- Identifica quién necesita qué resultado y para qué. Reutiliza términos del dominio, decisiones y plantilla existentes. No conviertas una instrucción técnica en una necesidad de negocio inventada.
- Separa reglas confirmadas, propuestas, preguntas y restricciones técnicas. Una práctica descrita en O'Reilly puede ayudar a redactar o descomponer una HU, pero no determina políticas, permisos o umbrales de la organización.
- Redacta criterios de aceptación observables, con ejemplos y excepciones relevantes. Usa Given/When/Then si el proyecto o el usuario lo requiere; no lo impongas a toda documentación.
- Si una historia tiene varias capacidades independientes, propone una división que conserve valor comprobable. Identifica dependencias sin inventar responsables, estimaciones o compromisos.
- Vincula cada criterio con la regla o necesidad que lo justifica. Explica las preguntas que bloquean definir el comportamiento; no sustituyas sus respuestas por «buenas prácticas».
- Para documentación técnica, verifica el contenido contra código y configuración disponibles. Actualiza el documento solicitado y conserva trazabilidad de decisiones. No afirmes que un comando o ejemplo se ejecutó si no ocurrió.

Entrega la HU o el documento listo para revisar. No añadas implementación ni publiques tickets cuando la tarea solo pida redacción.
